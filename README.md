# Conversation Checkpoints

**让模型在平台自动压缩之前，为后续的自己写一份可检查的续接提示。**

长对话接近上下文窗口上限时，Claude Code 会自动压缩历史；Claude.ai 在启用相应上下文管理功能时，也会摘要较早的消息。默认机制解决的是“让会话继续运行”：系统决定何时压缩，并生成一份替代旧历史的摘要。摘要可能足以保留任务概况，却未必保留某个长期对话真正需要的决策依据、约束和未完成事项。Claude Code 也提供 `/compact`、`/autocompact` 等控制；这里讨论的是默认自动流程，而不是说产品完全无法手动控制或观察。

这个项目采用另一条路径：**在默认压缩到来之前，由应用按自己的阈值发起一次隔离的模型请求，让模型阅读当前会话，写出供下一阶段使用的 checkpoint。** 生成规则放在一份独立的专用 prompt 中，不混入日常聊天的 system prompt。这样，压缩的时机、写作目标、保留范围和最终文本都可以由应用明确管理。

> 当前实例使用约 200k token 的上下文配置，因此选择在一次正常回复完成、输入用量达到约 **160k** 时启动 checkpoint。这是本实例的提前量，并非 Claude Code 或 Claude.ai 的统一阈值；不同模型与配置的窗口大小可能不同。

## 它不是普通的聊天摘要

普通摘要通常回答“刚才聊了什么”。checkpoint 要回答的是：**如果下一轮只能看到这份文字和最近几轮原文，模型需要知道什么，才能准确继续工作？** 因此它更像模型写给后续模型的一份上下文提示，而不是聊天记录的缩写。

专用生成 prompt 的公开架构如下；这里描述的是职责，不公开生产环境的 prompt 原文：

1. **定义任务**：把已发生的对话整理成可继续执行的 checkpoint，不续写聊天，也不凭空补全缺失信息。
2. **划分输入**：提供待替换的较早历史、上一份 checkpoint（若有）以及最近 15 轮完整对话作为参照。
3. **选择内容**：保留仍然有效的目标、决定及其理由、明确约束、已完成状态、待办事项和会影响后续判断的关键事实。
4. **控制失真**：区分已确认事实、推断和未解决问题；避免把暂时讨论写成最终决定，也避免重复、空泛或无依据的总结。
5. **面向续接输出**：写成下一阶段模型可直接使用的结构化上下文，重点是准确性和可操作性，而不是复述每条消息。

生成 checkpoint 的模型请求与正常聊天隔离：它使用独立 prompt，不携带日常对话的 system prompt 或工具配置，也不调用聊天工具。**模型负责写 checkpoint；专用 prompt 由使用者维护。** 当前实现使用单独的模型路由，因此这里的“模型为自己写”指面向同一会话的后续模型续接，并不意味着一定由正在聊天的同一模型实例生成。

## 当前工作流程

```text
正常对话完成一轮
        ↓
读取该轮最终模型调用的输入 token 用量
        ↓ 达到约 160k，且已有至少 15 轮用户对话
隔离请求：旧历史 + 上一份 checkpoint + 最近 15 轮参照 + 专用 prompt
        ↓
模型生成新的 checkpoint
        ↓ 校验输出、源历史和备份
新 checkpoint + 最近 15 轮完整原文 → 后续对话上下文
```

旧 checkpoint 在新版本成功生成并通过校验前一直保留；替换成功后，活动上下文只留一份 checkpoint。最近 15 轮保留原文，避免把刚发生的细节再次压缩。如果生成失败、响应不完整或会话在生成期间发生变化，旧上下文保持不变，不把未验证的文本注入下一轮。

这个仓库目前只分享设计思路。生产 prompt、私人对话、模型回执和服务端备份不在此仓库中。
