# Claude Code `-p` 接入网关与会话 Checkpoint

从直接调用 Claude API，迁移到由 Claude Code `-p` 驱动的聊天服务，再在应用层管理长对话的上下文。这个仓库分享的是**整体架构框架**，重点是让模型在平台默认自动压缩之前，为后续会话写一份可检查、可替换的 checkpoint。

## 架构总览

```text
                           ┌───────────── PWA / Telegram ─────────────┐
                           │ 消息、历史展示、prompt 编辑和状态控制      │
                           └────────────────┬─────────────────────────┘
                                            ↓
                           应用接入层：鉴权、会话路由、窗口状态和回执
                                            ↓
                           聊天服务：Claude Code 常驻 `-p` / `--resume`
                                ├── 本地会话与工具协议（含 MCP）
                                └── 本机请求网关 → 配置的上游模型 API

                           独立 checkpoint 任务 → 上游模型 API
                                └── 校验后更新聊天上下文与可见历史
```

早期聊天路径由应用直接组装请求并调用 Claude API。迁移后，Claude Code `-p` 负责模型会话与续接，PWA 仍负责用户可见的聊天记录和控制界面。**这里的“网关”是自己部署的接入与请求转发层，不是自建模型，也不是绕开上游 API。** `-p` 最终仍通过配置的模型提供方处理请求。

当前实现有两处容易混淆的转发层：

| 层 | 位置 | 主要职责 |
| --- | --- | --- |
| 应用路由 | PWA 与聊天服务之间 | 将窗口和接口请求送到对应服务，返回消息与状态 |
| 本机请求网关 | Claude Code `-p` 与上游 API 之间 | 对模型请求做有限、受控的兼容处理，转发流式响应并保留回执 |

checkpoint 是聊天服务管理的**独立模型请求**，不通过 Claude Code 的普通聊天工具循环。这样，生成摘要的 prompt 可以与日常聊天 prompt 分开管理。

## 为什么自己管理压缩

长对话接近上下文窗口上限时，Claude Code 默认会自动压缩历史；Claude.ai 在启用相应上下文管理功能时，也会摘要较早的消息。通用自动压缩的目标是腾出空间继续对话，其摘要不一定按某个应用需要的决策、约束和未完成事项来组织。Claude Code 同时提供 `/compact`、`/autocompact` 等手动和配置入口；这里比较的是默认自动流程与应用自己控制的流程。

当前实例关闭 Claude Code 的原生**自动**压缩，由应用在一次正常回复完成后读取该轮最终模型调用的输入用量。当它达到约 **160k token**、且已有至少 15 轮用户对话时，启动隔离的 checkpoint 任务。此实例按约 200k 的上下文配置预留提前量；160k 不是 Claude Code 或 Claude.ai 的统一阈值。

普通摘要通常回答“刚才聊了什么”。checkpoint 要回答的是：**如果下一轮只能看到这份文字和最近 15 轮原文，模型需要知道什么，才能准确继续工作？** 它更像模型写给后续模型的一份上下文提示。

## 专用 prompt 的公开框架

生成规则由使用者维护在独立 prompt 中；**模型写 checkpoint，而不是模型自己改写这份规则。** 下面只描述职责，不公开生产 prompt 原文：

1. **定义任务**：把历史整理成供下一阶段继续使用的上下文，不续写聊天，不补造缺失事实。
2. **划分输入**：提供待替换的较早历史、上一份 checkpoint（若有），以及最近 15 轮完整对话作为参照。
3. **选择内容**：保留当前目标、已确认决定及依据、有效约束、完成状态、待办事项和关键事实。
4. **控制失真**：区分事实、推断与开放问题；避免把讨论中的方案写成最终决定，也避免重复与空泛表述。
5. **面向续接输出**：形成下一阶段模型可直接使用的结构化文本，强调准确性与可操作性。

生成任务使用单独的模型路由，不携带日常聊天的 system prompt 或工具配置，也不调用聊天工具。因此“模型为后续自己写”指为同一会话的后续模型提供上下文，不保证是正在聊天的同一个模型实例。

## Checkpoint 如何落地

```text
正常对话完成 → 测量最终输入用量 → 达到阈值
                                    ↓
旧历史 + 上一份 checkpoint + 最近 15 轮参照 + 专用 prompt
                                    ↓
                            模型生成 checkpoint
                                    ↓
                       校验输出、源历史和备份
                                    ↓
                   新 checkpoint + 最近 15 轮完整原文
```

旧 checkpoint 在新版本成功生成并通过校验前一直保留。替换成功后，活动上下文只保留一份 checkpoint；最近 15 轮继续保留原文。生成失败、响应不完整或源会话变化时，原上下文不变，未验证的文本不会注入后续会话。

本仓库目前只公开设计框架。生产 prompt、私人对话、凭据、模型回执和服务端备份不在这里。
